# Data contract: `pacs.008` and `pacs.002`

What the SPI mock validates and how it answers. Derived from `spi.5.13.2/xlsx/PACS008.xlsx` and `PACS002.xlsx`
(sheets `pacs.008`, `pacs.002` and `Tabela de Domínios`), schemas `pacs.008.spi.1.16` and `pacs.002.spi.1.18`.
The XLSX files are the source of truth; this page is a working summary for the mock. `pacs.004` and `trck.002` are
read when their slices start.

The mock validates **by hand, in code** (no XSD library), and checks itself with contract tests against the XSDs and
the sample messages in `spi.5.13.2/exemplos/`.

## Scope of the mock

| Supported | Not supported (rejected or ignored) |
|-----------|-------------------------------------|
| Purpose `IPAY` (purchase or transfer), initiation forms `MANU` and `DICT` | Pix Saque and Pix Troco (`GSCB`, `OTHR`), Split Payment (`Tax`), MED refunds (`REFU`, `IPRT`), Pix Automático (`AUTO`), QR code and NFC forms, initiator (`InitgPty`) |
| Priorities `PAGPRI` (primary channel) | Fraud analysis (`PAGFRD`) and scheduling (`PAGAGD`, secondary channel) in the first version |
| Account types `CACC`, `SVGS`, `TRAN` | `OTHR` (PI account) and `SLRY` as creditor |

Rejecting an unsupported feature uses `CH16` (content incompatible with the business rules), generated by the SPI.

## Message envelope

Each message is an `Envelope` with `AppHdr` (`Fr`, `To`, `BizMsgIdr`, `MsgDefIdr`, `CreDt`, `Sgntr`) and a `Document`.
The mock ignores the signature (`Sgntr`).

## `pacs.008`: fields the mock checks

Multiplicity is the Brazilian one (`Mult. Brasil`). "Req" means `[1..1]`.

| Field (XML tag) | Req | Rule |
|-----------------|-----|------|
| `idMensagem` (`GrpHdr/MsgId`) | yes | 32 characters: `M` + sender ISPB (8, `[0-9A-Z]`) + 23 alphanumeric `[a-zA-Z0-9]`. Case sensitive. Must be unique per sender |
| `dataHoraCriacaoParaEmissao` (`CreDtTm`) | yes | UTC, `YYYY-MM-DD'T'hh:mm:ss.sss'Z'`. Invalid or out-of-range date: `DT02` |
| `quantidadeTransacoes` (`NbOfTxs`) | yes | Number `>= 1`, equal to the count of `CdtTrfTxInf`. Mismatch: `AM18` |
| `metodoLiquidacao` (`SttlmMtd`) | yes | `CLRG` |
| `prioridadePagamento` (`InstrPrty`) | yes | `HIGH` or `NORM` |
| `tipoPrioridadePagamento` (`SvcLvl/Prtry`) | yes | `HIGH` goes with `PAGPRI`; `NORM` goes with `PAGFRD` or `PAGAGD` |
| `CdtTrfTxInf` | yes | `[1..10]` for `PAGPRI` and `PAGFRD`; `[1..500]` for `PAGAGD` |
| `idFimAFim` (`PmtId/EndToEndId`) | yes | 32 characters: `E` + ISPB of the agent that generated it (8) + `yyyyMMddHHmm` in UTC (12) + 11 alphanumeric. Time within 12 hours (past or future) of processing. Unique across all operations sent to the SPI. Malformed: `FF08` |
| `idConciliacaoRecebedor` (`TxId`) | no | Up to 35 alphanumeric. Not used by the mock |
| `valor` (`IntrBkSttlmAmt`) | yes | Attribute `Ccy="BRL"`; up to 18 digits, 2 decimals, dot separator. Zero: `AM01` |
| `dataHoraRecebimentoPeloParticipanteDoUsuarioPagador` (`AccptncDtTm`) | yes | UTC date and time |
| `participanteTarifado` (`ChrgBr`) | yes | `SLEV` |
| `formaDeIniciacao` (`MndtRltdInf/Tp/LclInstrm/Prtry`) | yes | `MANU` or `DICT` in the mock |
| `nomeUsuarioPagador` (`Dbtr/Nm`) | yes | Up to 140 characters |
| `cpfCnpjUsuarioPagador` (`Dbtr/Id/PrvtId/Othr/Id`) | yes | 11 digits (CPF) or 14 alphanumeric (CNPJ) |
| `contaUsuarioPagador` (`DbtrAcct/Id/Othr/Id`) | yes | Up to 20 alphanumeric |
| `agenciaUsuarioPagador` (`.../Issr`) | no | Up to 4 digits, no check digit |
| `tipoContaUsuarioPagador` (`DbtrAcct/Tp/Cd`) | yes | `CACC`, `SVGS` or `TRAN` |
| `participanteDoUsuarioPagador` (`DbtrAgt/.../MmbId`) | yes | ISPB (8). Unknown: `RC09` |
| `participanteDoUsuarioRecebedor` (`CdtrAgt/.../MmbId`) | yes | ISPB (8). Unknown: `RC10` |
| `cpfCnpjUsuarioRecebedor` (`Cdtr/Id/PrvtId/Othr/Id`) | yes | 11 digits (CPF) or 14 alphanumeric (CNPJ) |
| `contaUsuarioRecebedor` (`CdtrAcct/Id/Othr/Id`) | yes | Up to 20 alphanumeric |
| `agenciaUsuarioRecebedor` (`.../Issr`) | no | Up to 4 digits |
| `tipoContaUsuarioRecebedor` (`CdtrAcct/Tp/Cd`) | yes | `CACC`, `SVGS` or `TRAN`; `SLRY` is not allowed (receives no payments): `AG03` |
| `idContaTransacional` (`CdtrAcct/Prxy/Id`) | by form | Required when `formaDeIniciacao` is `DICT` (the Pix key); must be absent when `MANU` |
| `finalidadeDaTransacao` (`Purp/Cd`) | yes | `IPAY` in the mock. Otherwise `CH16` |
| `informacoesEntreUsuarios` (`RmtInf/Ustrd`) | no | Up to 140 characters |

Consistency rules from the sheet: for `REFU` and `IPRT` the priority must be `HIGH` and the form `MANU`; for `IPAY` the
block `Structured` must not be filled.

Checks the SPI makes that depend on the mock's state, not on the message alone:

| Check | Rejection | Generated by |
|-------|-----------|--------------|
| Payer or receiver participant not registered | `DS27` / `RC09` / `RC10` | SPI |
| Payer and receiver are the same participant (book transfer) | `AG12` | SPI |
| `idFimAFim` already used in another operation | `DU03` is for charges settled elsewhere; for a repeated `pacs.008` the SPI is idempotent and returns the original outcome | SPI |
| The payer participant has no funds in its PI account | `AM04` (out of scope: no liquidity management) | SPI |
| No answer from the receiving participant within 40 s | `AB03` | SPI |

## `pacs.002`: fields the mock sends and reads

| Field (XML tag) | Rule |
|-----------------|------|
| `idMensagem` (`MsgId`) | Same format as in `pacs.008` (`M` + ISPB of the sender + 23) |
| `idInstrucaoOriginal` (`OrgnlInstrId`) | The `idFimAFim` of the original `pacs.008` (or the `idOperacao` of a `pacs.004`) |
| `idFimAFimOriginal` (`OrgnlEndToEndId`) | The `idFimAFim` of the original message |
| `situacaoDaTransacao` (`TxSts`) | `ACSP`, `ACSC`, `ACCC` or `RJCT` |
| `codigoDeErro` (`StsRsnInf/Rsn/Cd`) | Optional; a reason code from the table below, with `RJCT` |
| `detalhamentoDoErro` (`AddtlInf`) | Optional; up to 105 characters |
| `dataHoraLiquidacao` (`FctvIntrBkSttlmDt/DtTm`) | **Only the SPI fills it**, after settlement; participants must not |
| `dataContabil` (`OrgnlTxRef/IntrBkSttlmDt`) | **Only the SPI fills it**: accounting date, `YYYY-MM-DD` |

### Status values

| Code | Who sends it | Meaning |
|------|--------------|---------|
| `ACSP` | Receiving participant to the SPI | Order accepted after the receiver's checks |
| `ACSC` | SPI to the payer's participant | Payment settled |
| `ACCC` | SPI to the receiver's participant | Payment settled; the receiver can credit the account |
| `RJCT` | SPI or receiving participant | Order or return rejected, with a reason |

The sample messages follow this: `pacs.002_PSP_*` carry `ACSP`, `pacs.002_SPI_*` carry `ACCC`, `pacs.002_ERRO_*` carry
`RJCT` with `AB03`.

### Reason codes

Subset used by the mock for `pacs.008` (the full table, 52 rows, is in `PACS002.xlsx`). "Generated by" is as the
catalog states it.

| Code | Meaning | Generated by |
|------|---------|--------------|
| `AB03` | Settlement interrupted by timeout in the SPI | SPI |
| `AB11` | Timeout of the participant that sent the order | SPI |
| `AC03` | Branch and/or account of the receiver nonexistent or invalid | Receiving participant |
| `AC06` | Receiver account blocked | Receiving participant |
| `AC07` | Receiver account closed | Receiving participant |
| `AC14` | Wrong type for the receiver account | Receiving participant |
| `AG03` | Transaction not supported on the account (for example transfer to a salary account) | Receiving participant |
| `AG12` | Book transfer not allowed: payer and receiver at the same institution | SPI |
| `AM01` | Order with zero amount | SPI |
| `AM02` | Amount above the limit of the credited account type | Receiving participant |
| `AM04` | Insufficient funds in the payer participant's PI account | SPI |
| `AM18` | Invalid number of transactions | SPI |
| `BE01` | Receiver CPF/CNPJ inconsistent with the account holder | Receiving participant |
| `CH11` | Receiver CPF/CNPJ incorrect | Receiving participant |
| `CH16` | Message content incorrect or incompatible with the business rules | SPI |
| `DS04` | Order rejected by the receiving participant (generic) | Receiving participant |
| `DS27` | Participant not registered or not yet operating in the SPI | SPI |
| `DT02` | Invalid message date and time | SPI |
| `ED05` | Generic processing error | SPI or receiving participant |
| `FF08` | `idFimAFim` malformed | SPI |
| `FRAD` | Rejected on suspicion of fraud | Receiving participant |
| `RC09` | Payer participant ISPB invalid or nonexistent | SPI |
| `RC10` | Receiver participant ISPB invalid or nonexistent | SPI |

For returns (`pacs.004`, later): `AG13` (return of a return), `AM09` (returned amount above the original), `DT05` (past
the return deadline).

## What this changes in the design

- **`ACSC` versus `ACCC`.** The wallet as payer receives `ACSC`; as receiver it receives `ACCC` after answering `ACSP`.
- **Book transfer through the SPI is rejected with `AG12`.** A payment between two wallet customers sent to the SPI
  must fail, which confirms the rule in [architecture](../../../../docs/architecture.md): it is settled in the
  wallet's ledger and only reported afterwards.
- **Insufficient funds (`AM04`) is about the participant's PI account**, not the customer's balance. The mock has no
  liquidity management, so it never produces it, unless a test asks for it.
